# スケッチ: インフレ・発行台帳・破産処理(2026-10-03、未採用)

作業スキーマ(スケッチ → 〇〇Guide.md → 本採用)の最初の段階。決定事項と「案」を分けて書く。
前提: `dev/pricing-guide.md`(価格は全て手間賃10E/日から導出)、`dev/pricing-settings.md` §6-1(経済の縮尺)。

## 決定事項(作者の方針)
- 現実と同じ仕組みにする。インフレ率は**プレイヤーの活動量**で上がる。
- 貴金属もインフレで値上がりし、資産としてカウントされる。HRMHRMの会計は貴金属資産で裏打ちされている設定。
- エメラルドの増刷機能は現状ない。市場にエメラルドを流す単独機能が必要かもしれない。
- 破産の扱い:
  - **村**: 破産=人口減=壊滅。そのまま放置。村が持っていたお金は誰も回収しない(消える)。立て直しはプレイヤーだけが行う(村人を増やせるのはプレイヤーのみ。コマンドで増やさない)。
  - **法人**: 破産の内容により、HRMHRMが買い取るなどして救済する。
- HRMHRMの資金繰りは、貴金属の保有 / 株式市場への放出 / 市場にある品の生産、で自力で工面できる設定。
- **活動量は発行量ベースで測る**(2026-10-04決定)。取引回数や納品数のような行動回数は、操作(水増し取引)できそうなので使わない。台帳の income と credit の純増(`getNetIssuance`)が入力になる。market(資産との交換)・conversion(入出金)は含めない。
- 動物交易・PB・生鮮市場は、将来の取引所や「PB型の拡張ショップ」で置き換える予定なので、当面は**外貨を無から出す扱いのまま**で台帳には載せない(外貨・株・商品の換算記録は見送り)。
- **名目額の物価連動**(2026-10-04決定): 銀行金利・送料・プライム週額・保険料は物価に連動させる。配当は株価が動くので連動させない。融資・カードの金利は別途(銀行金利との差=スプレッドで持つ案)。
- **エメラルドの発行は、HRMHRMに括り付けず独立した機能にする**(2026-10-04決定)。HRMHRMはその機能に「申請」して発行してもらう立場。将来のアプデで、金利と発行をプレイヤーが決められるようにする。
- **価格は「ベース × 初期掛率 × インフレ指数」**(2026-10-04決定、案A)。今の価格(`village-pricing.js` の出力)はベースで、実際の価格は読む時に掛率を掛けて出す。目安は、大体どの品も数百〜数千Eになる大きさ(ベースの中央値が約5Eなので、初期掛率は100〜数百が候補。値は未決)。
  - 初期掛率を大きく取る理由: プレイヤーは自動化などで生産するため、手作業の労働費から出したベース価格のままでは安すぎる。
  - PBは、安い品をわざわざ売らず、一点物などを売るインセンティブにする方向(PB型の拡張ショップで一点物を扱う)。
  - 名目額(送料・プライム・保険料・融資枠など)は「ベース単位で持って掛率を掛ける」形にする。
- プレイヤー不在の世界は、村・法人・HRMHRMの三者で回る閉じた系(物価は凍結、活動した分だけ動く)。

## 案(未確定。検討のたたき台)
1. **発行台帳**: エメラルドが増減する処理(クエスト賃金・利息・融資・売却/購入・送料・手数料・清算)を、全部 `mint` / `burn` 相当の1関数経由にして発行量・回収量を計測する。
2. **物価水準の係数**: アクティブプレイヤー1人あたりの流通量(÷実体経済量)から算出。手間賃に掛け、価格式に反映する。
   - 価格は「読む時」に係数を掛ける(現状のバルクbaseRate焼き込み・モブ/PB/郵便の読み込み時固定計算は作り直しが必要)。
   - クエスト賃金は `labor-data.js` の直書きをやめ、手間賃からの計算式にする。
   - 変動は週ごとに上限をかけて暴走(活動→インフレ→賃金上昇→報酬増)を防ぐ。
3. **名目額の扱い**: 銀行金利・融資金利・送料・プライム週額・保険料・配当を、物価連動にするか固定にするか決める。銀行金利は物価と対(実質金利)で設計する案。
4. **貴金属**: 労働費から導出しているので手間賃に連動して上がる。必要なら物価より強めに動かす(実質金利が下がると買われる)。
5. **HRMHRMの注入**: HRMHRMが買い手として払う形(買い注文・公共事業クエスト・派遣/不動産収益の払い出し)にすると会計と一致する。注入量は活動量に比例させ、基礎分は小さく。
6. **破産処理の判定(法人)**: 事業価値 vs 債務で、買い取り救済 / 清算を決める。救済額にはHRMHRMの口座に応じた上限を設ける。清算で消える債務は burn として台帳に記録。
7. **ソロ環境でのデフレ対策**: 回収だけ進んで流通量が縮む場合の下支え。
8. **追いつき方式**: 誰もいない間はtickで回さず、画面を開いた時にまとめて追いつく(`pb.js` の `ensurePbFresh` と同じ考え方)。

## 金融政策機能の構想(案。独立機能としての発行)
- **役割を3つに分ける**:
  1. 発行機関(独立機能): 政策金利と発行量(新しく出すエメラルド)を持つ。台帳に新カテゴリ(例: `policy_issue`、グループ `issuance`)で記録し、`getNetIssuance` に含める。
  2. 申請者: HRMHRMなど。発行機関に「いくら・何のために」を申請する。承認されると、申請者の口座に入る。
  3. 決定者: 今は自動ルール(物価水準と発行上限から機械的に決める)。後のアプデで、プレイヤー(投票・役職)に差し替える。
- **決定者の差し替えを前提にした作り**: 政策パラメータ(政策金利・期間あたりの発行上限・承認条件)をデータとして1か所に持ち、「誰が決めるか」を関数1つに閉じ込める。今は `decidePolicy()` が自動、将来は投票結果を返す。
- **申請の中身(案)**: 申請者・金額・理由の分類(資金繰り/公共事業/買い取り救済など)・返済の有無(融資型 or 贈与型)。融資型なら返済で `burn`(out)、贈与型は純増になる。
- **歯止め(案)**: 期間あたりの発行上限、物価上昇率が閾値を超えたら承認を止める、申請者ごとの上限(HRMHRMが毎回無制限に出せない)。
- **銀行金利との関係**: 銀行金利は政策金利に連動する(政策金利 − 預金スプレッド)。今の週1.5%固定は、政策金利を初期値1つ持つ形に置き換える。
- 台帳はそのまま使える(カテゴリとグループを足すだけ)。

## インフレ指数の自動更新(2026-10-05決定・実装済み)
- **上限は週0.05%(4週で約0.2%)**。ワールドの1週間=7日=現実の約2時間20分なので、1ワールド年(52週)で約2.6%、現実並みの穏やかなインフレ。活動量連動だと上がりすぎるので、上限で頭打ちにする。
- 式: `週の上昇率 = 上限 × tanh(圧力)`、`圧力 = 1人あたり純増(ベース単位) ÷ 週の標準収入(70E)`。純増は台帳の income + credit の in − out、1人あたりはその週に income/credit の流れがあったプレイヤー数で割る。
- **下方硬直**: 純増が負でも指数は下げない(0止まり)。プレイヤー不在の週は凍結。
- 欠けた週は台帳の記録に従って順に処理(追いつき方式)。記録の無い週は上昇率0。処理済みの週は覚えるので二重に上がらない。
- 実装: `economy/inflation.js`(`updatePriceIndex`)。`market-engine.js` の1分ごとの処理から呼ぶ。台帳は週ごとの活動プレイヤー数も持つようになった。
- **注意(要判断)**: 銀行金利(週1.5%)・カード金利(週3%)は、インフレ(週0.05%)の30〜60倍。ゲーム的な誇張として独立に置いているが、「金利は政策金利と連動」(未実装)にするなら、ここの水準も合わせて決め直す必要がある。

## 2026-10-05 の決定(HRMHRMの会計まわり)
- 既存ワールドの×64換算を既定にする(資産は導入時に合わせる)。
- 口座テンプレートに貴金属の時価評価を含める。
- 精算不能が3週を超えたら介入。村は人口0なら登録解除・人口ありなら介入。法人は介入(内容によりHRMHRMが買い取り救済など)。
- 取引所は別アプデ。`quest_listing` と取引の出品の統合は保留。まずHRMHRMが自動で動けるようにする(実装済み: `hrmhrm-accounting.md`)。
- 発行の承認ルールの具体値(期間あたりの上限など)は、上の介入ルールとは別の話として、まだ決まっていない。

## 2026-10-06 の決定(開発銀行機構)
- 法人はHRMHRMの機能から派生する。口座・運用は共通(HRMHRM専用は初期の資本金と台帳からの収益・費用の部分だけ)。
- **独立機関の開発銀行機構**が、申請元の資産を見て判断する: 売りに出せそうなものがあれば**申請を却下して資産を売りに出させる**。なさそうなら**最低限の運用に必要な分を支給**する。(実装済み: `development-bank.md`)
- これは、前に書いた「HRMHRMが申請する発行機関」の具体化。発行の承認ルールの具体値は、判断基準のパラメータ(`devbank_*`)として持ち、将来プレイヤーの議論で変えられる。

## 金融政策の呼び出し口(2026-10-05決定・実装済み)
- 方針: 今後のアプデで「プレイヤー同士の議論でパラメータを変える」機能を入れる。今回は**仕組みだけ**(`economy/policy.js`)。議論・投票そのものは未実装。
- パラメータ(週あたりの率): 政策金利 / カードの上乗せ / ローンの基本上乗せ / ローンの難易度ごとの上乗せ / 融資(貸し手)の利幅 / 現金配当の上乗せ。インフレ指数の上限など「設計上の安全装置」は対象外。
- 変更の入口は `setPolicyParam(key, value, { source })` 1つ。誰が決めるかを知らない(`source` は履歴に残る名前)。将来の議論機能は、これを呼ぶだけでよい。
- 安全装置: 範囲(min〜max。forceでも破れない) / 1回の変更幅 / 変更間隔(1週) / パラメータ間の制約(カード金利 ≧ 最高のローン金利。forceでも破れない)。force(管理者の緊急用)は幅と間隔だけ破れる。
- 履歴(直近50件)と、変更の購読(`subscribePolicyChange`。ニュース告知などに使える)、全リセット(`resetAllPolicyParams`)がある。
- 管理コマンド: `/scriptevent bmh:policy list | get <key> | set <key> <値> [force] | reset <key|all> | history [件数]`。
- 「ブロック換算はしなくていい」は、物理エメラルド・エメラルドブロックとの換算には触れない、という意味で受け取った(要確認)。

## 金利・保険・既存ワールド(2026-10-05決定・実装済み)
- **金利は政策金利+上乗せ**(`economy/rates.js`)。インフレ(週0.05%上限)に合わせ、政策金利は週0.06%(年約3.2%、実質金利ほぼ0)。
  - 預金 週0.06% / ローン(借入) 週0.12〜0.20%(難易度で上がる。スコアが高いと最大0.04%引き) / カード(リボ) 週0.30%(年約15.6%) / 融資(貸し手)は貸し倒れを織り込んだ水準。
  - 以前は預金1.5%・カード3%・ローン2〜8%(週)で、インフレの30〜60倍以上だった。順序は 預金 < ローン < カード を保つ(検算で確認)。
  - 将来、政策金利をプレイヤーが決める時は、上の「金融政策の呼び出し口」(`policy.js`)から変更する。
  - 融資(貸し手): 借り手の返済確率を0.80〜0.99に変更(以前は0.4〜0.97)、週利は貸し倒れ分を織り込んで算出、満期の利息は「週利×期間」の単純利息(以前の×4の補正は廃止)。
- **保険の支給額を引き上げ**: 1回の支給の価値 = 週の保険料 × 4(`INSURANCE_PAYOUT_MULTIPLE`)。支給の個数は基準価格から出す(海難: 鉄80個 / 漁獲: 乾燥コンブ92個 / 海底財産: 金76個)。週に4回に1回以上死ぬ人なら元が取れる水準。保険料も支給品の価値も掛率に比例するので、インフレしても比は変わらない。
- **既存ワールドへの導入**(`economy/migration.js`): 旧縮尺で保存されている金額を、プレイヤーの初回ログイン時に1回だけ掛率で換算する(口座残高・借入・カード・融資元本・株の取得単価・外貨の取得レート・先物の約定価格・派遣マージン)。基準は賃金なので、資産が何日分の労働に当たるかは変わらない。換算した口座の増分は台帳に conversion として記録(発行ではない)。新版で始まったワールド(台帳か物価指数がある)は換算しない。外貨の単位数・株数・物理エメラルド・村人の賃金は換算しない(村人の賃金はベース単位で保存済み)。

## 実装状況(2026-10-04)
- **掛率の層も実装済み**: `scripts/economy/price-level.js`。**初期掛率 = 64**(決定)、インフレ指数は1.0から(今は `/scriptevent bmh:pricelevel [指数]` で手動のみ)。
  - 読む時に掛ける: 小口・バルク・株・外貨・先物の市場価格、郵便販売の価格。
  - 名目額も掛率経由: 送料・プライム週額・保険料・融資枠・カード枠と最低返済・クエスト賃金・村人の賃金・派遣マージン・違約金・登録の祝い金・先物の証拠金・配当/ストックオプションのしきい値・電子取引の上限(`getMaxETx`)。
  - 契約時に金額が確定して保存されるもの(クエスト報酬・融資・カード枠・派遣マージン)は、その時点の名目額で保存。後からインフレしても借入額は変わらない(現実の借金と同じ)。
  - 村人の賃金は**ベース単位で保存**し、支払い・表示の時に掛率を掛ける(インフレに追従)。
  - 外貨レート・株価も掛率で動くので、動物交易・PBの外貨建て価格(単位数)は変わらない。
  - 電子取引の上限 `MAX_E_TX` は、現状どこでも強制していなかった(定数のみ)。関数 `getMaxETx()` を用意した。
- **案1(発行台帳)は実装済み**: `scripts/economy/ledger.js`(サブレポジトリ `dev/archive/wage-revision/` の `ledger` コミット)。
  - 口座のエメラルド(`acc_emeralds`)を増減する全箇所(14ファイル・約35箇所)を `creditEmeralds` / `debitEmeralds` / `applyEmeraldDelta` 経由に置換。直接書き込みは `check_ledger.mjs` が検出する。
  - 記録: カテゴリ別の in(システム→プレイヤー)/ out(回収)を、累計と直近12週の週別で保持(world動的プロパティ `bmh_ledger_v1`、約7KB/上限32KB)。
  - カテゴリは6グループ: income(賃金・派遣・雇用ボーナス・利息・配当)/ credit(融資・カード)/ market(ゴーレム・バルク・外貨・株・先物)/ spend(送料・プライム・保険)/ penalty / conversion(物理エメラルドの入出金)。
  - 恒等式「全プレイヤー残高の合計 = 台帳の in − out」を検算スクリプトで確認済み。
  - 管理用: `/scriptevent bmh:ledger [週数]` で集計表示。`getNetIssuance(週数)` が income+credit の純増(インフレ率の入力候補)。
  - **ゲーム挙動・価格は一切変えていない**(記録するだけ)。
- 未対応: 外貨(HNY等)・株・商品の台帳、プレイヤー間取引、台帳開始前の既存残高(開始時点の総量は不明なので、見るのはフロー=増減であって総量そのものではない)。

## 注意点(議論で出たもの)
- HRMHRMが貴金属を売ると市場の供給が増えて値下がりし、資産価値も減る(危機時ほど悪化)。
- 株の放出はHRM株を持つプレイヤーの持ち分を薄める。ストックオプションの既存付与とも重なるので、出す条件と上限を決める。
- 三者だけの閉じた系は、お金の偏り・取引の停止・破産の連鎖が起きやすい。村側に人口・季節に応じた需要の揺らぎを入れて取引を回し続ける。
