## 今後のアプデの流れ(案、2026-10-05時点)

これまでに決まった方針(価格→実機→法人テンプレート、取引所化、村・法人の破産、プレイヤー議論での金融政策)を、
依存関係で並べ直したもの。順番と区切りは提案で、固定ではない。

```
[今]   価格のオーバーホール(実装済み。0.4.3として0.4.2に適用済み)  ← いまここ(①の実機確認)
  │
  ▼
①  実機確認 + 配布(版は0.4.3。既存ワールドは初回ログインで自動換算。バックアップ必須)
  │   ・配布用の Bee-My-Honey-043.zip は作成済み(0.4.2に適用しただけ。manifestは未更新=作者が更新する)
  │   手順: dev/real-device-checklist.md
  ▼
②  テンプレートの残りと会計の土台  ← 法人テンプレート
  │   ・[済] 口座テンプレート + HRMHRMの会計と自動運用(貴金属の時価評価・週次の締め・資金繰り。hrmhrm-accounting.md)
  │   ・[済・0.4.5] クエスト掲示(日替わり4件・受注/納品/放棄・受注者の表示。`quest-template-spec.md`)と人材派遣契約(ジャンル→運営主体→施設→プール→換金。`dispatch-spec.md`)
  │   ・quest_listing の issuer 拡張(company / player の発注。slots / claimedBy の枠は用意済み)
  │   ・村・法人の口座の作成(登録の仕組み)
  ▼
③  発行機関と破産処理   ← ②の口座が前提
  │   ・[済] 開発銀行機構(独立機関。申請を審査: 売れる資産があれば却下して売却 / なければ最低限の運用資金を支給。development-bank.md)
  │   ・政策金利の変更・発行量の決定をプレイヤーの議論に渡す(policy.js の呼び出し口は実装済み。devbank_* も対象)
  │   ・介入のルール(決定済み・判定は実装済み): 精算不能が3週超 → 村は人口0なら登録解除/人口ありなら介入、法人は介入
  │   ・介入の中身(法人の買い取り救済 or 清算)は法人テンプレートの実装時に決める
  ▼
④  P2P共通基盤と取引所(別アプデ。quest_listingと出品の統合は保留)
  │   ・郵便販売の取引所化(HRMHRMの常設出品 standingStock + プレイヤーの出品)
  │   ・動物交易・PB・生鮮市場の置き換え(PB型の拡張ショップ。外貨を「無から」出さない形へ)
  │   ・個人は1シュルカーまでの制約を、法人格の登録と合わせて解禁
  ▼
⑤  村の法人格化(上位職解放クエスト)
  │   ・ベル+光るイカスミで村を登録、人口から余剰/欠乏を出してバルク取引
  │   ・ライセンスの biome単一値 → region:*配列への書き換えを同時に行う
  ▼
⑥  プレイヤーの議論による金融政策・株式上場
      ・議論・投票の機能が setPolicyParam(..., { source: "vote:..." }) を呼ぶ
      ・プレイヤーによる株式上場
```

## 0.4.5 — ローン・銀行履歴・クエスト・派遣・プール・初回の仕事(2026-10-09。実装済み。実機確認は一部済み)

仕様は `dev/quest-template-spec.md`(クエスト)と `dev/dispatch-spec.md`(派遣)。ゲーム外の検算は `dev/check_labor.mjs` / `dev/check_loan.mjs`。
- **ローン**: 「融資管理」(借入・貸付の確認)と繰上返済。トグルで「元本のみ」/「利息込み全額」。既存ローンは元本の記録が無く、元本のみ=全額返済。
- **銀行の入出金履歴**: プレイヤーごとに直近30件(`ledger.js` の `getAccountHistory`)。`creditEmeralds(..., { from })` / `debitEmeralds(..., { to })` で相手を渡す。預金利息は同じ週で1行にまとめる。
- **クエスト**: 掲示は日付が種のワールド共通4件(カテゴリごとに1件)。受注・納品・放棄、受注者の一覧(ワールド側)、受けた週の終わりで期限切れ(遅延判定)。型は `delivery` のみ実装(`defeat / action / score` は枠だけ。到達・守る・所持・クラフトは入れない)。
- **派遣**: ジャンル(農場/鉱山/工場)→ 運営主体 → 日数。契約時に産出(品目と個数)が確定し、回収で HRMHRM のプールに入る。産出 = 賃金 × 日数 × `dispatch_output_ratio` ÷ 基準価格。
- **プール換金**: HRMHRM の週の締めで、保持数(`pool_keep_per_item`)を超えた分をその時の売値で換金して収益に入れる。現物は資産には載せない(取引所とつなぐ時に決める)。
- **初回の仕事**: スタッフサービスを初めて使う(実績がない)人に「初めてのアルバイト」(報告するだけ)を出し、シュルカーボックスを1個渡す。実績がある人には出さない。登録の仕組みができたらスターターキットへ移す。
- **実機確認の結果(2026-10-09)**: プールの換金は設計どおり(小麦1269→640、ビートルート1045→640、鉄の原石・バケツは保持数未満で据え置き。現金の減少と週の損益が一致)。初回の仕事も動作確認済み。
- **除名**: 村人の履歴書の通算派遣日数が `resume_tenure_days`(1095日)に達したら、自動で除名。手動の解雇は付けない(手違いの解雇を防ぐため)。
- **設定値(`policy.js`)**: `quest_max_active`(2)/ `dispatch_output_ratio`(1)/ `resume_tenure_days`(1095)/ `pool_keep_per_item`(640)/ `pool_sale_ratio`(1)。
- 未実装・次: プールの保持数を「価値ベース」にする(個数だと高い品目が売れ残る。例: バケツ396個)/ プールの引き出し(出庫)はバルク取引かチェストにする/ 保持数のプレイヤー数比例と、原石→加工品のサプライチェーンは取引所のアプデで/ company/player 発のクエストと法人の施設(出力先がチェスト)/ 派遣の日数の選択肢を増やす / defeat・action・score の判定 / 入出金履歴の画面の拡張(絞り込みなど)。

### 全体方針
現状のマイルストーンは基本的に「1プレイヤー対システム(HRMHRM)」の設計で、マルチプレイ要素(プレイヤー間の直接取引)がまだない。今後は、現状HRMHRMが仲介しているアイテム/お金の取引・クエスト・人材派遣を、すべてプレイヤー同士でも機能させたい。また、ソロプレイでも村人が経済の一員であることが実感できるようにしたい。そのため次の大型アップデートは、単発の「会社」機能というより以下の2本柱として捉える。

### 柱1: 取引・クエスト・人材派遣を貫くP2P共通基盤
- `quest_listing`(issuer/requirement/reward/status/claimedBy)は0.3.1で先取り実装済み。issuerを`company`/`player`に広げる形で流用予定
- 現状バラバラの3実装(取引=通販、クエスト=労働市場、人材派遣=オーナーズクラブ)を、共通の「発注/受注」骨格に寄せる
- 郵便販売の取引所化: HRMHRMが常時規定数を高めの価格で出品しつつ、プレイヤーも出品してマージンを稼げるようにする構想。「HRMHRMは放置していても村人が自動消化して稼ぐが、プレイヤーが介入して初めて価値が世界に循環する」という設計思想
- プレイヤーによる株式上場もこの延長線上

### 柱2: NPCが自律的に経済活動を続ける仕組み
- HRMHRMの自社口座(資本金)構想。村人・HRMHRMがバックグラウンドで勝手に経済活動を続け(誰も見てなくても仕事を消化する、口座残高が動く)、ソロプレイでも経済の一員であることが伝わるようにする

### テンプレート設計(柱1・2の前提タスク)
上記2本柱に着手する前に、下記のテンプレートを書き出す。これがないと村人が動けない。

- **`workers_resume`(既存)** — 村人・プレイヤー共通の履歴書。「NPCが自律的に働く」を入れるなら、現状の受動的なフィールド(records/skills/licenses)だけで足りるか要検討
- **`quest_listing`(既存、拡張要)** — issuerを`player`/`company`に開放する部分の詳細仕様がまだない
- **取引/出品テンプレート(未定義)** — 通販・取引所でのアイテム出品用。`quest_listing`と統合するか別建てにするか未決定
- **口座テンプレート(未定義)** — HRMHRM自身や将来の「会社」が持つ資本金・収支を表す型。個人プレイヤーの口座(既存のwallet)とは別に必要
- **人材派遣契約テンプレート(未定義)** — オーナーズクラブの「派遣中」状態は今`workers_resume`側の運用フィールド(status/dispatchEndDay等)に間借りしている状態なので、独立した契約テンプレートにするか判断が必要

- `food-data.js`のコメントには「未登録の食品は暫定でRAW扱い(フォールバック)」「isFood判定は呼び出し側(スキャン処理)で行う想定」とあるが、実装されていない(コメントと実装の食い違い。どちらかに揃える)

**方針: カスタムアイテムは自動認識する(登録ガイドは置かない)**
- サーバーではカスタムアイテムが当たり前なので、BMHに認識させるための登録手順を利用者に求めない
- ただし「認識」と「値付け」は別: 鮮度は既定値で自動化できるが、価格・ジャンルは自動で決められない。辞書にない品は取引(バルク/生鮮市場)の対象外にする。漏れの洗い出しは`data/item-dictionary.js`の`checkItemFacetCoverage`を使う想定

**検討: 「砂糖・金系の素材を含むレシピは自動で腐らない」(未着手)**
- 手動の`NEVER_SPOIL_ITEMS`を減らす目的。スクリプトからゲーム内のレシピ材料は引けない(調べた範囲では該当APIなし)ため、開発時にレシピデータから「砂糖・金を含む食品」を抽出して表に焼き込む形になる。カスタムアイテムのレシピは読めないので対象外
- クッキーは材料が小麦とカカオ豆で砂糖を含まないため、自動判定から漏れる(例外指定が残る)
- 「材料が3つ以上」という個数ベースの判定は不採用: 種類数でも合計個数でも、腐らないでほしい5種と腐ってほしい料理(シチュー、パン等)の境目がきれいに分かれない

**検討: クラフト/調理を経た食品は加工扱いにする(未着手、調査のみ)**
- 調べた範囲(ドキュメント確認のみ、実機未確認): `PlayerCraftRecipeAfterEvent`(ベータ)は完成品のスタックとブロックが取れるが、材料は取れない。`RecipeCraftingContext`(ベータ、ブロックコンポーネント`minecraft:recipe_crafting`経由)は入力スロットと完成品を読めるが、ドキュメントの例はストーンカッターで、作業台に対応しているかは未確認。かまど・燻製器の調理を検知する手段は見つからなかった
- どちらもベータAPI(ワールド設定の「ベータAPI」実験機能が必要。実績が解除されなくなる可能性が高い)。配布先の環境を絞るため、安定版APIだけで済む判定(食品コンポーネント+既定値)を土台にして、クラフト連動は任意で後付けする方針
- 完成品は新品扱いになるので、腐りかけの材料をクラフトすると鮮度が戻る点にも注意(材料の最も古いスタンプを引き継ぐ案あり)
- 先にやること: クラフト完了イベントを購読して、作業台で発火するか・ブロックが取れるかをログに出す小さなスクリプトで実機確認
