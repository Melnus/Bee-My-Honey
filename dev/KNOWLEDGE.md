# Bee-My-Honey 開発ナレッジ(教訓集)

このファイルは、`MILESTONES.md`(何を作ったか)や`CONVENTIONS.md`(何を守るべきか)とは別に、
「実際にハマった話」「作り込んでから方針転換した話」を記録する場所です。
同じ失敗を繰り返さないために、新しいセッションはこのファイルにも目を通してください。

## 1. Script APIの制約はシミュレータでは発見できない

v0.4.0の食品鮮度システムは、シミュレータ(Node上のモック)では全ての経路が問題なく動いていた。
ところが実機のBedrockでは、魚・肉・農作物などのスタック可能な食品が一切腐らなかった(v0.4.1で修正)。

原因は`ItemStack.setDynamicProperty`がスタック可能なアイテムに対しては
`UnsupportedFunctionalityError`で失敗するという、シミュレータには存在しない実機だけの制約だった。
経過tickをこの動的プロパティに保存する設計だったため、毎回書き込みに失敗して経過が0に戻り続けていた。

**教訓:** シミュレータで全部通っても、新しい仕組みは実機で最低1回は確認すること。
具体的な既知の制約一覧は`CONVENTIONS.md` §6を参照。

## 2. 抽象的な取引単位は、実アイテムのスタック単位(64)との関係を先に決めておく

#2(材木取引)の先物構想では、当初「1ロット=苗木1本あたりの平均最大収穫量(38本)」を
27スロット(シュルカー)に合わせて32に丸め、「1シュルカー=27ロット=864原木」という換算を作った。

ところが27ロットという集め方は、Minecraft本来のスタック単位(64個/スタック、
1,728個/シュルカー)とは無関係な、ロット数をシュルカーのスロット数に合わせただけの数字だった。
そのため「引き出し時の実アイテムの物理容量」と「先物の取引単位」が、同じ「1シュルカー」という
呼び方なのに別の数字(864 vs 1,728)を指す、という混乱を生んでいた。

途中で「32はそもそも64の半分(半スタック)にしたかっただけ」と気づき、
1単位=32本のままスロット数の掛け算をやめれば、54単位=1,728本=シュルカー満載、と
端数なく綺麗に繋がることが分かった。

**教訓:** ゲーム内の抽象的な取引単位(ロット・口・株など)を設計するときは、
「Minecraft本来のスタック単位(64)の何倍・何分の1か」を先に確認する。
たまたま別の数字(スロット数など)に合わせて掛け算すると、意味の異なる2つの「1単位」が
同じ名前で並走してしまう。

(なお、この材木先物システム自体は下記3の理由で最終的に撤回されたため、
現行コードには「サップ」という単位は存在しない。)

## 3. 需要が具体化する前に、複雑な仕組みを作り込みすぎない

#2(材木取引)は当初、SWB(キツネ)画面に専用の「材木取引」画面を作り、
苗木を対象にした先物取引(単位「サップ」、7日契約、電子倉庫での保有など)まで
仕様を詰めて実装した。

しかし後になって、(1) 専用画面を作るより原木を丸石等と同じ一般資源(bulkOnly)に
統合した方が導線がシンプルであること、(2) 先物特有の仕組みは、将来P2P共通基盤(柱1)で
取引所ができれば市場が自然に価格発見するはずで、今作り込むには過剰であることに気づき、
先物システムを**撤回・削除**した。現状は原木8種類を一般資源に統合しただけになっている。

**教訓:** 「あったら面白そう」な複雑な仕組み(先物・専用マーケットなど)は、
実際にその需要が具体的に見えるまで作り込みすぎない。仕様を詰める議論自体は無駄ではないが、
実装に落とす前に「もっとシンプルな既存の仕組みに統合できないか」を必ず一度疑う。

## 4. 実装が先に進んだら、ドキュメントもその場で直す

`tag-dictionary.js`のコメントには、しばらくの間
「GENRE_TAGSは生鮮市場の水産物(`genre:seafood`)のみ登録済みで、肉類等は未確定事項(G-4)の
解消を待つ」という記述が残っていた。しかし実際のコードでは、#3の実装時点で
肉類(`genre:meat`)・農作物(`genre:produce`)・乳卵(`genre:dairy`)の3ジャンルも
とっくに追加済みで、記述だけが古いままになっていた。

**教訓:** 「後で追記する」「未確定」と書いたコメントは、実際に追記した瞬間に消すか書き換える。
コードとドキュメントがズレると、次のセッション(または未来の自分)が
「まだ実装されていない」と誤解して二度手間になる。
