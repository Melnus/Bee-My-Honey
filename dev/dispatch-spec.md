# 派遣契約テンプレートの決め打ち(案)

2026-10-07 の会話で決まった方針をまとめた。対象は 0.4.5(ローン・クエスト・派遣・銀行履歴)。
オーナーズクラブの派遣は、**村人の履歴書を施設に送るだけ**。村人の実体は登録時に消えているので、派遣中も帰還の処理は要らない。

---

## 1. 流れ

派遣する → ①ジャンル(農場 / 鉱山 / 工場)→ ②運営主体(HRMHRM / プレイヤーA / …)→ 日数を選ぶ → 契約

- 運営主体が1つしかない間は、②を自動で飛ばす。
- 0.4.5 で実装するのは `operator: "hrmhrm"` の3施設だけ。`company` は枠だけ残す。
- 派遣が完了した時点で、施設の産出を出力先に入れ、マージンを口座へ振り込む。

---

## 2. データの形

```js
facility = {
  id,                                   // "hrmhrm_farm" など
  genre: "farm" | "mine" | "factory",   // 名前空間は facility:* (食品の genre:* とは別)
  operator: { type: "hrmhrm" | "company", id: null },
  output: { table: [ { itemId, weight } ] },   // 産出表(施設ごと)
  sink: { type: "pool", poolId }               // HRMHRM公共施設
      | { type: "container", location }        // プレイヤー法人の施設(将来)
}

dispatch_contract = {            // 村人(履歴書)の dispatch 項目を置き換える
  employeeId, facilityId,
  startDay, days,                // 完了日 = startDay + days
  wage,                          // 契約時の1日あたり賃金(ベース単位。グレード・レベル込み)
  margin                         // 契約時に確定する名目額
}
```

履歴書(`employee`)に足す項目:
- `dispatchedDaysTotal`: 通算の派遣日数(完了のたびに加算)。除名の判定に使う。既存の履歴書は 0 から数える。

---

## 3. 産出量

**産出の価値 = 契約時の賃金(ベース単位)× 派遣日数 × 産出係数。個数 = 産出の価値 ÷ 品目の基準価格(切り捨て、最低1個)。**

- 賃金は `OWNER_BASE_WAGE_PER_DAY(20E) × グレード倍率(C1.0 / B1.4 / A2.0 / S3.0) × (1 + (レベル−1)×0.2)`。すでに履歴書に持っている値を使う。
- 品目の基準価格は、価格エンジンの値(`pricing-guide.md` の原価。バルクの基準 `baseRate`、郵便販売の基準価格)をそのまま使う。新しい価格表は作らない。
- 産出係数は政策パラメータ `dispatch_output_ratio` にする(初期値 1.0)。調整はここだけで済む。
- 品目は、派遣ごとに産出表から重み付きで1種類を抽選する。

**1日あたりの個数の例(グレード・レベル1、係数1.0、ベース単位の価格)**

| グレード(賃金/日) | 農場(0.188E) | 鉱山: 鉄(0.407E) | 鉱山: 金(0.532E) | 鉱山: ダイヤ(1.5E) | 工場(5E品) |
|---|---|---|---|---|---|
| C(20E) | 106 | 49 | 37 | 13 | 4 |
| B(28E) | 148 | 68 | 52 | 18 | 5 |
| A(40E) | 212 | 98 | 75 | 26 | 8 |
| S(60E) | 319 | 147 | 112 | 40 | 12 |

- 価格は `pricing-scale-table.md` の第0章(バルク)と、`pricing-guide.md`(採集の汎用値 約0.188E)から。工場の5Eは郵便販売の中央値。**実際の個数は、価格エンジンの値で決まる。**
- 最低グレードで「数個」になるのは、鉱山のダイヤと工場品。農場は100個を超える。農場も数個にしたいなら、係数を下げる(0.25 なら C で 農場26 / 鉄12 / 金9 / ダイヤ3 / 工場1)。

---

## 4. プール(現物倉庫)と換金

- HRMHRM の施設の産出は、プールに溜まる(ワールドの動的プロパティ `hrmhrm_pool`。品目ID → 個数)。
- 取引所ができたら、プールを常設出品の在庫として共通に使う(`standingStock`)。今は溜まるだけ。
- **週の締めで換金する**(0.4.5 に入れる)。HRMHRM の週次処理の中で、品目ごとに保持数(`pool_keep_per_item`、初期値640)を超えた分だけを、その時の売値(基準価格 × 現在の掛率 × `pool_sale_ratio`、初期値1)で換金し、HRMHRM の現金と週の収益に入れる。
- 換金は市場(外部の相手方)への売却として扱うので、台帳(プレイヤーとのお金のやり取り)には載せない。
- 会計: 賃金・マージンは費用として今まで通り台帳から計上される。プールの現物は**資産には載せない**(換金した時に収益として入る)。現物を資産として載せるのは、取引所とつなぐ時に決める。

---

## 5. 除名(3年で解雇)

- 村人の履歴書の `dispatchedDaysTotal` が、3年分に達したら除名する。現実の派遣の3年ルールに合わせる。
- 3年分は政策パラメータ `resume_tenure_days` にする(初期値 1095日 = 365日×3)。範囲は 365〜3650。
- 判定は、派遣が完了して `dispatchedDaysTotal` を加算した直後に行う。**自動でしか起きない。手動で解雇する操作は入れない。**
- 除名の中身: 履歴書を削除し、通知を出す。事故率の計算に使う登録数からも外れる。
- 目安: ゲーム内の1日は約20分なので、1095日は約365時間(連続で約15日)になる。短く感じたら設定値を下げる。
- 対象は村人だけ。プレイヤー自身の履歴書(スタッフサービス)は対象外。
- 事故での除名は今まで通り。事故率の考え方(登録数が多いと上がる)も変えない。

---

## 6. 口座・履歴

- マージンは `creditEmeralds(player, margin, FLOW.DISPATCH_MARGIN, { from: "HRMHRM" })` で振り込む。銀行の入出金履歴に「派遣マージン(HRMHRMから)」と残る。
- 賃金・人件費・事故補償を HRMHRM 口座経由にする方針は、クエスト報酬と同じ。会計は `hrmhrm.js` の週次の締めが台帳から計上する。

---

## 7. 決定済み / 未決

**決定済み**
- 派遣は履歴書を施設に送るだけ。解雇の操作は付けない。
- 選択の順は ジャンル → 運営主体。0.4.5 は HRMHRM の3施設のみ。
- 産出量は賃金の価値から逆算する。売値(換金)は時価。
- 除名は通算3年分の派遣日数で自動。設定値で変えられる。日数は人に掛かるので、履歴書ごとに数える(施設ごとにはしない)。
- `dispatch_output_ratio` の初期値は 1.0。

**未決**
- プールの現物を HRMHRM の資産として会計に載せるか(取引所とつなぐ時に決める。今は換金時の収益だけ)。

**0.4.5 で決めたこと(追加)**
- プールの換金は週の締めで行う。保持数の初期値は640(10スタック)、掛け率の初期値は1(その時の売値のまま)。
